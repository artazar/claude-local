## Code style
- No magic numbers — name constants.
- Functions should do one thing. If it needs a comment to explain what it does, split it.
- Always use memory-optimized and cpu-optimized approach when creating new logic.

## Communication
- Be concise. Prefer short responses unless depth is explicitly asked for.
- Be laconic and to the point, do not repeat same summary thoughts multiple times.
- Don't explain what you're about to do — just do it, then summarize briefly.
- If you're uncertain, say so directly. Don't hedge with filler phrases.
- When I ask "why", explain reasoning before giving the answer.

## Working style
- For tasks with 3+ steps, show a brief plan first and wait for approval.
- If you encounter ambiguity, ask ONE clarifying question — not five.
- Flag when you're about to do something irreversible (delete, overwrite, restructure).
- Always clean up built artifacts after work.

## Testing
- Write tests for any non-trivial logic unless I say otherwise.
- Prefer unit tests over integration tests for pure functions.
- Don't mock things you could test directly.

## Documentation
- Do NOT update README files or any other docs when you apply bug fixes or make small changes.

## When in doubt
- If you don't know, say "I don't know" — don't hallucinate an answer.
- Before deleting or overwriting anything, confirm with me.
- If a task seems underspecified, surface the ambiguity rather than guessing.
